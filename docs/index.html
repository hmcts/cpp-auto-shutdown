Design notes for the build story

Six columns, one question each

Every column answers something a DM actually asks: whose is it, what's it for, is it up, when does it go down, and is my exception live. Nothing on the row requires knowing how the pipeline works.

State now is the observed value from state/environments/*.json — never inferred from the clock — carrying aggregateStatus plus the per-component line beneath it. Where it disagrees with the schedule the row carries a quiet not what the schedule expects flag rather than a headline metric.

A failed check never blanks the record

When verification fails or a run publishes no artifact, the writer keeps the last good observation and alerts — it never persists unknown. So a failed check shows up as an observation that stops getting newer, not as an empty one.

That gives two different rows: Last checked 14.5 hours ago — a check may have failed where a record exists but has gone stale, and Never checked where a stack is in the schedule but has no verified result at all. They mean different things and need different follow-up, so they don't share a label.

Components on the row, reasons behind it

The state record carries AKS, IaaS and PaaS separately, so the row does too: which components a stack has, and whether each is up. A stack whose AKS is up but PaaS is stopped reads Partly up · AKS up · PaaS down — not “not known”, because that state is known and specifically wrong. DMs use these component names already, so they stay as they are.

What stays behind Detail is the why: each component's verification reason, the observation's age, and its source pipeline and run ID. A DM needs to see that PaaS is down; they escalate the timeout reason rather than debug it.

Say what it does, not how it works

Automation reads merged configuration only, so a request that hasn't been applied does nothing. But merged, PR and main are our words, not a DM's — so the board says Not approved, Approved, not applied, Approved from 10 Sep, Active now and Ended.

The two blocked states are split because they need different people. Not approved means chase an approver; Approved, not applied means approval happened but the change never reached the schedule — a platform problem, and one a single “not applied” label would have sent the DM chasing the wrong person for.

None of them use the word yet on its own: yet implies it is on track, when nothing happens without someone acting. Each carries the consequence beside it — won't apply, stack still shuts down — because the state alone doesn't tell a DM what to do.

Component names (AKS, IaaS, PaaS) stay technical because DMs already use them. Pipeline numbers and run IDs stay in Detail, where they help whoever gets escalated to.

Baseline is 06:00–19:00; delays to 21:00 / 23:00 / 24h and weekend presets show as the effective shutdown time, not as config syntax.
